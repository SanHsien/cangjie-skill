# 阶段 1.6 — 独立 Skill 晋级门（产品化验证）

## 为什么需要这一步

阶段 1.5 回答的是"这个候选是否值得保留"（知识验证）。它没有回答第二个问题：
**它是否值得成为一个独立、可发现、可安装的 Skill**（产品化验证）。

把每个通过验证的知识点都变成独立 Skill，会制造安装负担、命名理解成本，以及相邻能力
之间的触发竞争。上游的《纳瓦尔宝典》样本因此产出 19 个 Skill，那是真实读者反馈
"Skill 太多"的直接来源。

晋级门把"知识保留"和"Skill 数量"解耦：**未晋级的方法完整保留在 `verified.md` 里，
不会被删掉，也不会失联**——它们只是不各自成为一个可安装的 Skill。

与阶段 0.5 的分工：0.5 在**开工前**判断这份内容该做成什么形态（整包 / 少量 skill /
替代产物 / 不该蒸）；1.6 在**验证之后**判断已通过的单元里哪些该独立出来。前者管
"要不要做"，后者管"做出来长几个"。

## 五条判据

一个候选只有同时满足以下条件，才有资格成为晋级 Skill：

| # | 判据 | 问题 | 要求 |
|---|---|---|---|
| 1 | 独立意图 | 用户会不提书名、单独提出这个任务吗？ | **必须通过** |
| 2 | 独立契约 | 有自己的输入、步骤、输出和完成标准，不只是一个观点或术语？ | **必须通过** |
| 3 | 独立运行 | 不加载全书或多个兄弟能力也能正确执行？ | **必须通过** |
| 4 | 独立复用 | 预计会在多个任务／项目中重复调用，或需要被其他 Skill 组合？ | 与 5 至少 1 条通过 |
| 5 | 独立评测 | 能写出明确的正向、负向、近邻和输出断言？ | 与 4 至少 1 条通过 |

## 执行步骤

1. 对 `verified.md` 中每个单元逐条评审五条判据，记录布尔结果与一句话理由。
2. 判定写回 **`verified.md` 该单元的条目**，用一行 `晋级: promoted | router` 加理由。
   本 fork 的流水线产物是 Markdown（`verified.md`、`rejected/`、`INDEX.md`），没有
   Capability Bundle（`verified.yaml`）也没有 `destinations.json`，所以判定就记在
   知识单元原本待着的地方，不另开一份会和它漂移的索引。
3. **检查预算**：可发现入口总数（1 个来源路由入口 + 晋级 Skill 数）默认软预算 **8**。
   超出时按预期调用频率、跨场景复用、独特性、证据强度和触发可分性排序，超出预算的
   候选先降为 `router`；只有用户明确要求穷尽式产出、且验证证明不能安全合并时才允许超过。
4. 阶段 3 建 `INDEX.md` 时，`router` 单元列在来源路由入口底下（它们仍然可被找到），
   `promoted` 单元各自出现在 skill 总览里。

## 硬规则

- 不能为了压数量，把输出契约不同的能力强行拼成一个模糊 Skill；
- 未晋级候选**不进入 `rejected/`**——它们通过了知识验证，只是不单独发现。
  `rejected/` 的语义是"没通过验证"，混进来会让事后捞回失去意义；
- 晋级 Skill 与来源路由入口必须互有近邻负例（阶段 4 验证），避免同一请求双触发。
